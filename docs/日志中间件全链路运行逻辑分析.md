# 日志中间件全链路运行逻辑分析报告

## 一、系统架构概览

日志系统覆盖三个层次：**应用层**（Go 服务）→ **采集层**（Filebeat）→ **存储与查询层**（Elasticsearch + Kibana）。

```
┌─────────────────────────────────────────────────────────────────────┐
│                         应用层（Go 服务）                            │
│                                                                     │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐          │
│  │  HTTP 请求    │───>│  Logger      │───>│  utils/      │          │
│  │              │    │  Middleware   │    │  logger.go   │          │
│  └──────────────┘    └──────────────┘    └──────┬───────┘          │
│                                                  │                  │
│                                          写入 JSON 日志文件         │
│                                          ./logs/2026-06-05.log     │
└──────────────────────────────────────────┼──────────────────────────┘
                                           │
                                           ▼
┌─────────────────────────────────────────────────────────────────────┐
│                         采集层（Filebeat）                           │
│                                                                     │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐          │
│  │  监控日志文件  │───>│  JSON 解析    │───>│  添加元数据   │          │
│  │  *.log       │    │  keys_under   │    │  service/    │          │
│  │              │    │  _root        │    │  log_type    │          │
│  └──────────────┘    └──────────────┘    └──────┬───────┘          │
│                                                  │                  │
└──────────────────────────────────────────┼──────────────────────────┘
                                           │
                                           ▼
┌─────────────────────────────────────────────────────────────────────┐
│                    存储与查询层（ES + Kibana）                        │
│                                                                     │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐          │
│  │  Elasticsearch│   │  ILM 策略    │    │  Kibana      │          │
│  │  索引存储     │───>│  自动滚动    │    │  可视化查询   │          │
│  │  app-logs-*  │    │  7天自动删除  │    │  中文界面     │          │

└─────────────────────────────────────────────────────────────────────┘
```

### 两个服务的差异对照

| 对比项 | backend（后台管理系统） | shop-backend（C 端商城） |
| :--- | :--- | :--- |
| 服务名标识 | `backend` | `shop-backend` |
| 日志文件轮转 | 无（单文件/天） | 有（10MB 自动轮转） |
| 日志文件命名 | `2026-06-05.log` | `2026-06-05.log` → `2026-06-05_1.log` |
| 初始化方式 | `utils.InitLogger()` 显式调用 | `utils.InitLogger()` 显式调用 |
| 中间件逻辑 | 相同 | 相同 |
| Filebeat 采集路径 | `/logs/backend/*.log` | `/logs/shop-backend/*.log` |
| ES 索引路由 | `app-logs-*` | `app-logs-*` |

## 二、应用层：初始化流程

### 1. 启动序列

两个服务的初始化流程一致，均由 `main()` 显式调用 `InitLogger()`：

```
main() 启动
  │
  ├── utils.InitLogger()          ← 显式初始化（非 init() 自动执行）
  │     └── loggerOnce.Do()       ← sync.Once 保证只执行一次
  │           └── NewLogger()
  │                 ├── os.MkdirAll("./logs", 0755)
  │                 ├── generateLogFilePath() / 日期命名
  │                 ├── os.OpenFile(日志文件, O_APPEND|O_CREATE|O_WRONLY)
  │                 ├── log.New(文件, "", 0) × 3  ← info/warn/error 三个 Logger
  │                 ├── make(chan logEntry, 1000)  ← 带缓冲通道
  │                 └── go processLogs(serviceName) ← 启动异步消费协程
  │
  ├── utils.Info("日志系统初始化成功")
  ├── defer utils.CloseLogger()
  │
  ├── config.LoadConfig()
  ├── config.InitDB()
  ├── middleware.SetJWTSecret()
  │
  ├── gin.New()
  ├── r.Use(middleware.RequestLogger())  ← 注册日志中间件
  ├── r.Use(middleware.CORS())
  ├── r.Use(gin.Recovery())
  │
  └── r.Run(":" + port)
```

### 2. InitLogger 设计要点

使用 `sync.Once` + 显式调用替代 `init()` 自动执行，原因：

- **避免包导入副作用**：`init()` 在任何导入 `utils` 包的代码中都会自动执行（包括测试），导致测试时产生不必要的日志文件
- **初始化时机可控**：由 `main()` 决定何时初始化，可以在初始化前完成配置加载
- **nil 安全**：全局日志方法（`Info`/`Warn`/`Error`）添加了 `globalLogger == nil` 检查，未初始化时静默忽略，避免 panic

## 三、应用层：请求日志中间件

### 1. 中间件 8 阶段处理流程

`RequestLogger()` 中间件对每个 HTTP 请求执行以下 8 个阶段：

```
请求进入
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段 1：初始化请求上下文                                  │
│   • 生成 UUID 作为 RequestID                             │
│   • 存入 gin.Context（controllers.RequestIDKey）          │
│   • 添加到响应头 X-Request-ID                            │
│   • 记录开始时间 start = time.Now()                      │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段 2：检查是否跳过日志记录                              │
│   策略 1：路径过滤 shouldSkipPath()                      │
│     跳过 /api/captcha、/api/upload、/api/download 等     │
│   策略 2：Content-Type 过滤 shouldSkipLogging()          │
│     跳过 image/*、video/*、application/pdf 等二进制类型   │
│   策略 3：Base64 检测 isBase64Content()                  │
│     检测 data:image/;base64, 格式或高比例 base64 字符    │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段 3：读取请求体                                       │
│   • io.ReadAll(c.Request.Body) 读取完整请求体            │
│   • isBase64Content() 检测 base64 数据                   │
│   • truncateBody(body, 100KB) 截断超长内容               │
│   • io.NopCloser 写回请求体，供后续处理使用               │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段 4：准备响应体捕获                                    │
│   • 创建 bodyLogWriter 包装 c.Writer                     │
│   • bodyLogWriter 同时写入 bytes.Buffer 和原始 Writer     │
│   • 替换 c.Writer = blw                                  │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段 5：执行后续处理 c.Next()                            │
│   • 执行后续中间件                                       │
│   • 执行控制器逻辑                                       │
│   • 执行服务层逻辑                                       │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段 6：处理响应体                                       │
│   • 检查响应 Content-Type 是否为二进制类型                │
│   • isBase64Content() 检测响应中的 base64 数据            │
│   • truncateBody(blw.body.Bytes(), 100KB) 截断超长响应   │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段 7：构建日志字段                                      │
│   基础字段（始终记录）：                                   │
│     request_id / method / path / query / status          │
│     latency_ms / client_ip / user_agent                  │
│   条件字段：                                              │
│     skip_reason（跳过原因）                               │
│     request_body / request_body_raw（请求体）             │
│     response_body / response_body_raw（响应体）           │
│     error.code / error.message / error.detail（错误信息） │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段 8：记录日志                                         │
│   从 response_body.code 提取业务码 bizCode               │
│   根据业务码决定日志级别：                                 │
│     bizCode >= 5000 → utils.Error()（服务器错误）         │
│     bizCode >= 4000 → utils.Warn()（客户端错误）          │
│     其他           → utils.Info()（正常请求）             │
└─────────────────────────────────────────────────────────┘
```

### 2. 日志过滤策略

中间件实现了 4 层过滤策略，按优先级依次执行：

| 优先级 | 策略 | 实现函数 | 效果 |
| :--- | :--- | :--- | :--- |
| 1 | 路径过滤 | `shouldSkipPath()` | 跳过验证码、上传、下载等接口，不记录请求体和响应体 |
| 2 | Content-Type 过滤 | `shouldSkipLogging()` | 跳过图片、音频、视频、PDF 等二进制类型 |
| 3 | Base64 检测 | `isBase64Content()` | 检测并跳过包含大量 base64 编码的数据（如内嵌图片） |
| 4 | 大小限制 | `truncateBody()` | 超过 100KB 的内容自动截断，附加 `...(truncated)` 标记 |

**跳过原因记录**：即使请求被过滤，基础字段（method、path、status 等）仍然记录，并附加 `skip_reason` 字段说明跳过原因，便于排查问题。

### 3. 日志级别判定规则

日志级别由响应体中的业务码（`code` 字段）决定，与项目错误码规范对齐：

| 业务码范围 | 日志级别 | 含义 | 示例 |
| :--- | :--- | :--- | :--- |
| 0 | `INFO` | 成功 | 查询商品列表成功 |
| 4000-4999 | `WARN` | 客户端错误 | 参数缺失（4002）、登录失败（4013） |
| 5000+ | `ERROR` | 服务器错误 | 数据库错误（5001）、缓存错误（5002） |

## 四、应用层：日志记录器核心机制

### 1. 异步写入架构

```
业务代码                    通道                     后台协程                  文件
─────────                ──────                  ─────────               ──────

utils.Info("xxx")  ──>  logChan (1000)  ──>  processLogs()  ──>  ./logs/*.log
utils.Warn("xxx")  ──>      缓冲区         │  ├── checkAndRotate()
utils.Error("xxx") ──>                     │  ├── json.Marshal()
                                            │  └── logger.Println()
```

**关键设计**：

- **带缓冲通道**：`make(chan logEntry, 1000)`，缓冲区 1000 条，减少生产者阻塞
- **单协程消费**：`processLogs()` 是唯一的消费者，避免并发写入文件
- **互斥锁保护**：`sync.Mutex` 保护 `checkAndRotate()` 和 `rotateLogFile()`，防止轮转时并发冲突
- **优雅关闭**：`Close()` 先关闭通道，再 `wg.Wait()` 等待协程处理完剩余日志

### 2. shop-backend 日志文件轮转

shop-backend 实现了基于文件大小的自动轮转，backend 暂未实现。

**轮转流程**：

```
processLogs() 处理每条日志时
  │
  ├── checkAndRotate()
  │     ├── mu.Lock()
  │     ├── currentFile.Stat() 获取文件大小
  │     ├── size >= 10MB ?
  │     │     ├── 是 → rotateLogFile()
  │     │     │         ├── currentFile.Close()
  │     │     │         ├── generateNewLogFilePath()
  │     │     │         │     └── 找到下一个不存在的编号文件
  │     │     │         │         如 2026-06-05_1.log
  │     │     │         ├── os.OpenFile(新文件)
  │     │     │         └── SetOutput(新文件) × 3
  │     │     └── 否 → 继续写入当前文件
  │     └── mu.Unlock()
  │
  └── 写入日志
```

**文件命名规则**：

| 场景 | 文件名 | 说明 |
| :--- | :--- | :--- |
| 首次启动（无历史文件） | `2026-06-05.log` | 基础文件名 |
| 重启（基础文件已存在） | `2026-06-05_1.log` | 编号递增 |
| 再次重启 | `2026-06-05_2.log` | 继续递增 |
| 文件达到 10MB 轮转 | `2026-06-05_3.log` | 从 `_1` 开始找不存在的编号 |

### 3. 日志条目结构

每条日志以 JSON 格式写入文件，结构如下：

```json
{
  "timestamp": "2026-06-05T14:30:00+08:00",
  "level": "INFO",
  "message": "API请求: {\"request_id\":\"xxx\",\"method\":\"GET\",\"path\":\"/api/products\",...}",
  "caller": "product_controller.go:42",
  "service": "shop-backend"
}
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `timestamp` | string | ISO 8601 格式时间戳，带时区信息 |
| `level` | string | 日志级别：INFO / WARN / ERROR |
| `message` | string | 日志消息，中间件日志包含完整请求信息的 JSON |
| `caller` | string | 调用位置，格式为 `文件名:行号` |
| `service` | string | 服务名标识：`backend` 或 `shop-backend` |

### 4. 调用栈追踪

`getCallerInfo()` 使用 `runtime.Caller(3)` 跳过 3 层调用栈，定位到实际的业务调用者：

```
调用链：
  业务代码（如 product_controller.go:42）
    → utils.Info()                    ← 第 3 层（目标）
      → globalLogger.Info()           ← 第 2 层
        → logChan <- logEntry{}       ← 第 1 层
          → getCallerInfo()           ← 第 0 层
```

## 五、采集层：Filebeat 配置

### 1. 数据流

```
./logs/backend/*.log     ──┐
                           ├──> Filebeat ──> Elasticsearch
./logs/shop-backend/*.log ──┘           (app-logs-2026.06.05)

/var/lib/docker/containers/*/*.log ──> Filebeat ──> Elasticsearch
                                      (container-logs-2026.06.05)
```

### 2. 两个日志输入源

| 输入源 | 类型 | 路径 | ES 索引 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| backend 应用日志 | `log` | `/logs/backend/*.log` | `app-logs-*` | JSON 格式，自动解析 |
| shop-backend 应用日志 | `log` | `/logs/shop-backend/*.log` | `app-logs-*` | JSON 格式，自动解析 |
| Docker 容器日志 | `container` | `/var/lib/docker/containers/*/*.log` | `container-logs-*` | 自动添加 Docker 元数据 |

### 3. JSON 解析配置

Filebeat 对应用日志的 JSON 解析配置：

| 配置项 | 值 | 说明 |
| :--- | :--- | :--- |
| `json.keys_under_root` | `true` | JSON 字段放在事件根级别，而非嵌套在 `json` 对象下 |
| `json.add_error_key` | `true` | 解析失败时添加 `error.message` 和 `error.type` 字段 |
| `json.overwrite_keys` | `true` | JSON 中的 `@timestamp` 覆盖 Filebeat 的时间戳 |

### 4. 自定义字段

每个输入源添加两个自定义字段用于路由和筛选：

| 字段 | backend 值 | shop-backend 值 | 容器日志值 |
| :--- | :--- | :--- | :--- |
| `log_type` | `app` | `app` | `container` |
| `service` | `backend` | `shop-backend` | （无） |

### 5. 全局处理器

| 处理器 | 作用 | 条件 |
| :--- | :--- | :--- |
| `add_host_metadata` | 添加主机名、IP 地址、操作系统信息 | 非 container-logs |
| `drop_fields` | 删除 `agent`、`ecs`、`input`、`log.offset` 字段 | 所有事件 |

## 六、存储与查询层：Elasticsearch + Kibana

### 1. 索引模板（app-logs）

`app-logs-*` 索引的字段映射：

| 字段 | ES 类型 | 分词器 | 说明 |
| :--- | :--- | :--- | :--- |
| `@timestamp` | date | — | 日志时间戳，Filebeat 自动添加 |
| `log_level` | keyword | — | 日志级别，精确筛选（如只看 ERROR） |
| `message` | text | ik_max_word / ik_smart | 日志消息，支持中文分词搜索 |
| `service` | keyword | — | 服务名，按服务筛选 |
| `caller` | keyword | — | 调用位置，精确匹配 |
| `request_id` | keyword | — | 请求追踪 ID，链路追踪 |
| `method` | keyword | — | HTTP 方法 |
| `path` | keyword | — | 请求路径 |
| `status_code` | integer | — | HTTP 状态码 |
| `latency_ms` | long | — | 响应时间（毫秒），范围查询 |
| `client_ip` | keyword | — | 客户端 IP |
| `error_code` | integer | — | 业务错误码 |
| `error_message` | text | ik_max_word / ik_smart | 错误消息，中文分词搜索 |

**索引设置**：

| 配置 | 值 | 说明 |
| :--- | :--- | :--- |
| `number_of_shards` | 1 | 单节点部署，1 个分片 |
| `number_of_replicas` | 0 | 单节点无副本 |
| `lifecycle.name` | `app-logs-policy` | 绑定 ILM 策略 |
| `lifecycle.rollover_alias` | `app-logs` | 滚动索引别名 |

### 2. ILM 策略（索引生命周期管理）

| 阶段 | 触发条件 | 动作 | 说明 |
| :--- | :--- | :--- | :--- |
| hot | 索引存在超过 1 天 或 大小超过 500MB | rollover（滚动到新索引） | 热数据阶段，频繁读写 |
| delete | 滚动后 7 天 | 删除索引 | 自动清理过期数据 |

**数据保留周期**：一个日志索引最多保留约 8 天（1 天 hot + 7 天 delete 等待期）。

### 3. Logstash 数据同步

Logstash 用于 MySQL 业务数据同步到 Elasticsearch（非日志采集），当前配置了以下 Pipeline：

| Pipeline | 同步表 | 频率 | ES 索引 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| orders | orders + order_items | 15 秒 | orders | 订单数据增量同步 |
| products | products + skus | 60 秒 | products | 商品数据增量同步 |
| customers | customers | 60 秒 | customers | 客户数据增量同步 |
| users | users | 60 秒 | users | 用户数据增量同步 |

**注意**：日志采集不经过 Logstash，Filebeat 直接写入 Elasticsearch，效率更高。

### 4. Kibana 配置

| 配置 | 值 | 说明 |
| :--- | :--- | :--- |
| 访问地址 | `http://localhost:5601` | 浏览器访问 |
| 界面语言 | `zh-CN` | 中文界面 |
| ES 连接 | `http://elasticsearch:9200` | Docker 内部网络 |

## 七、全链路数据流示例

以一个完整的 API 请求为例，展示日志从产生到可查询的全过程：

```
1. 客户端发送请求
   GET /api/products?page=1

2. RequestLogger 中间件处理
   ├── 生成 RequestID: "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
   ├── 记录开始时间: 2026-06-05T14:30:00.000
   ├── 读取请求体: 空（GET 请求）
   ├── 包装 ResponseWriter
   └── c.Next() 执行后续处理

3. 控制器处理请求
   ├── ProductController.GetProducts()
   ├── ProductService.GetProducts()
   └── 返回 {"code": 0, "message": "success", "data": [...]}

4. 中间件后置处理
   ├── latency_ms: 45
   ├── bizCode = 0 → INFO 级别
   └── utils.Info("API请求: {...}")

5. 日志记录器处理
   ├── logChan <- logEntry{Level: "INFO", Message: "API请求: {...}"}
   ├── processLogs() 从通道读取
   ├── checkAndRotate() 检查文件大小
   ├── json.Marshal() 序列化
   └── infoLogger.Println(jsonStr) 写入文件

6. 日志文件内容
   {"timestamp":"2026-06-05T14:30:00+08:00","level":"INFO",
    "message":"API请求: {\"request_id\":\"a1b2c3d4-...\",\"method\":\"GET\",
    \"path\":\"/api/products\",\"status\":200,\"latency_ms\":45,...}",
    "caller":"logger.go:310","service":"shop-backend"}

7. Filebeat 采集
   ├── 监控 /logs/shop-backend/*.log
   ├── 检测到新行
   ├── JSON 解析：keys_under_root + overwrite_keys
   ├── 添加字段：log_type=app, service=shop-backend
   └── 路由到 app-logs-2026.06.05 索引

8. Elasticsearch 存储
   ├── 索引：app-logs-2026.06.05
   ├── 字段映射：log_level=keyword, message=text+ik分词, ...
   └── ILM：1 天后滚动，7 天后删除

9. Kibana 查询
   ├── 访问 http://localhost:5601
   ├── 在 Discover 中搜索：log_level: "ERROR"
   ├── 或搜索：message: "订单"（中文分词）
   └── 或按 request_id 追踪完整请求链路
```

## 八、协程安全与并发模型

### 1. 并发安全分析

| 组件 | 并发场景 | 安全机制 |
| :--- | :--- | :--- |
| `logChan` | 多协程写入，单协程读取 | Go 通道天然线程安全 |
| `processLogs()` | 单协程消费 | 无竞争 |
| `checkAndRotate()` | 在 `processLogs()` 内调用 | `sync.Mutex` 保护 |
| `rotateLogFile()` | 在 `checkAndRotate()` 内调用 | 由 Mutex 间接保护 |
| `globalLogger` | 多协程读取 | `sync.Once` 保证初始化安全 |

### 2. 关闭流程

```
应用收到终止信号
  │
  ├── defer utils.CloseLogger()
  │     ├── close(logChan)          ← 关闭通道，processLogs() 退出 range 循环
  │     ├── wg.Wait()               ← 等待 processLogs() 处理完剩余日志
  │     └── currentFile.Close()     ← 关闭日志文件（仅 shop-backend）
  │
  └── 应用退出
```
